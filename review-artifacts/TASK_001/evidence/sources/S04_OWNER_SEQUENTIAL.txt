# BRACU Course Tracker — Sequential Multi-Skill UI/UX Design Review

## Objective

Repository: https://github.com/sk-reyad/bracu-course-tracker

I want to personally review **every distinct, actionable UI/UX improvement recommended by the previously completed design-skill and plugin audits**, one recommendation at a time.

Do not perform a large redesign.

Do not implement all recommendations at once.

For each recommendation, create an isolated, working Before/After demonstration and STOP for my feedback.

Only start the next recommendation after I explicitly finish reviewing the current one.

**This is a sequential, user-controlled design-selection process, NOT production implementation.**

## 5. STRICT ONE-RECOMMENDATION-AT-A-TIME RULE

This is the most important instruction.

After preparing the master recommendation register:

**Select exactly ONE unreviewed recommendation.**

Prefer the highest-impact recommendation that has not already been selected or rejected.

For that one recommendation only:

1. Explain the problem.
2. Identify the recommending skills/plugins.
3. Show current implementation and evidence.
4. Propose the smallest meaningful improvement.
5. Implement it only in its isolated demo.
6. Verify functionality.
7. Capture actual Before/After evidence.
8. Present the comparison to me.
9. STOP and wait for my decision.

Do not implement the second recommendation.

Do not start another demo while I am reviewing the current one.

Do not treat silence, a test passing, or an old approval as permission to proceed.

## 6. How Every Before/After Must Be Presented

For each recommendation, include:

### A. Recommendation Information

- Recommendation number and audit ID.
- Exact skill/plugin attribution.
- Affected page or component.
- Why this change was recommended.
- Whether the issue is verified, inferred, or a design preference.

### B. BEFORE

Show the original component as it currently exists.

Use real browser screenshots captured from the unchanged baseline.

Describe the actual current behavior.

### C. AFTER

Show only this one proposed change.

Use a fully functional, isolated demo.

Preserve unrelated UI and behavior.

### D. Side-by-Side Comparison

Capture matched Before and After screenshots at identical viewport sizes, theme, zoom, application state, and sample data.

Provide relevant:

- Desktop view
- Mobile view
- Light mode
- Dark mode
- Hover/focus/active states where applicable

Do not use AI-generated mockups as evidence of browser implementation.

### E. Interactive Demo

Provide working local preview URLs or clear local launch instructions.

For interactive changes, demonstrate the actual user action.

For keyboard accessibility, record focus movement and keyboard behavior.

For motion changes, provide a short screen recording or animated comparison where tooling permits.

For performance changes, provide actual loading/network/performance evidence instead of pretending that a static screenshot demonstrates improvement.

If a recommendation cannot be meaningfully displayed visually, explain exactly how its behavioral effect can be observed.

### F. Code Changes

Show:

- Exact files changed
- Relevant selectors/functions
- A minimal isolated diff
- Any possible regression risk

### G. Verification

Run relevant tests, including actual browser checks wherever available.

Explicitly report:

- PASSED
- FAILED
- BLOCKED
- NOT TESTED

Never invent a successful test.

## 7. Keep Each Proposal Independent

Each recommendation must have its own isolated candidate implementation.

Do not silently accumulate previous experimental changes into the next comparison.

Maintain:

- Unchanged baseline
- Current candidate
- Separately preserved selected candidates
- Optional cumulative selected-only demo

The individual Before/After must always make it possible to identify what changed because of that particular recommendation.

A cumulative preview may be shown additionally, but only after the individual comparison is complete.

Do not merge conflicting aesthetic options.

## 8. Owner Decision Protocol

After presenting a single recommendation, ask me to choose:

**APPROVE**

I like the proposed change.

Store it as a selected candidate. Do not merge it into the original repository.

**REJECT**

I do not like the proposed change.

Record it as rejected and do not reintroduce it later under another skill name.

**REVISE**

I want changes to the current proposal.

Improve only this proposal and present another Before/After comparison. Do not move forward.

**SKIP / HOLD**

Do not select or reject yet. Preserve the proposal for later review.

Do not proceed to the next recommendation unless I explicitly instruct you to continue.

Approval of an individual demo is not authorization for production implementation.

## 10. Do Not Confuse Audit Recommendations With Mandatory Changes

Some recommendations are objective bugs:

- Broken focus management
- Unintended page overflow
- Missing accessible names

Others may be preferences:

- Less visual density
- Different spacing
- Different card emphasis
- More restrained styling

Treat these categories differently.

For subjective improvements, prioritize faithful visual comparisons and let me make the final design choice.

Do not insist that one aesthetic direction is correct simply because multiple tools recommended it.
