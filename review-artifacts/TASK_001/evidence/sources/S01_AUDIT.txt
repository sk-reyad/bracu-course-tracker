# BRACU Course Tracker — Frontend UI Multi-Skill Audit

## A. Executive Summary

BRACU Course Tracker is a vanilla HTML/CSS/JavaScript academic planning tool with a distinctive prerequisite roadmap, semester planning, course management, progress reporting, authentication, administration, support, maintenance, legal, and error surfaces. This audit was performed against local source at commit `9d86db46b1134a3755a2e269252b1ee1234f2570` on 2026-11-06 (Asia/Dhaka).

The application already has substantial strengths: a product-specific academic identity; strong separation between preview, authenticated, and privileged flows; explicit light/dark token families; responsive rules; semantic forms; loading/empty/error states; keyboard-aware admin controls; reduced-motion infrastructure; and unusually broad source/contract test coverage. The complete Node suite passed 365/365 tests.

The audit found **9 unique issues** after deduplication: **0 P0, 2 P1, 5 P2, and 2 P3**. The highest-impact findings are:

1. `F-002` — tracker dialogs open without moving or containing focus; Tab continues into the page behind the modal.
2. `F-003` — four tracker dialog close buttons are icon-only and have no accessible name.
3. `F-001` — hidden curriculum-stream tooltips create whole-document horizontal overflow at 360, 390, and 1280 px.
4. `F-005` — curriculum-stream triggers render only 13 px high, creating a small-target usability concern; WCAG spacing exceptions still require assessment.
5. `F-004` — Settings declares a tablist without tab/tabpanel roles, selection state, relationships, or arrow-key behavior.

No existing Impeccable audit report was present in this checkout. Impeccable 4.3.1 instruction files were found on disk during final availability verification, although omitted from the session catalog; the engine binary was absent from the checked bundled/cache locations. Its technical framework was applied manually, with the detector unavailable. Its critique was only partially applied: the prescribed isolated assessments were not performed. The historical 12/20 score therefore cannot be accepted or rejected as a like-for-like result. Accessibility and responsive edge cases remain despite strong source tests; the blue academic language and prerequisite roadmap are clear strengths.

### Coverage and limitations

- Real Chrome 156 headless rendering and Chrome DevTools Protocol measurements were completed against a loopback-only local preview.
- The required widths 360, 390, 768, 1024, 1280, and 1440 px were rendered for the tracker preview in light mode; dark mode was also rendered and computed-style verified at 390 px.
- Auth, maintenance, legal, and error surfaces were rendered at representative mobile/desktop widths. The unauthenticated Admin route redirected to the Admin sign-in view; the authenticated Admin Panel was source/test-audited but not rendered with credentials.
- No production accounts, student data, database writes, Supabase changes, imports, or privileged actions were used.
- The in-app Browser plugin was unavailable. Playwright and axe-core were not installed; no dependencies were installed. Core Web Vitals, full screen-reader testing, hosted OAuth/MFA, authenticated student/admin flows, production middleware behavior, and true PDF print output remain unverified.
- There was no committed screenshot baseline, so visual-regression status is **INCONCLUSIVE**, not PASS.

## Canonical Finding Register

### F-001 — Hidden curriculum tooltips cause document-level horizontal scrolling

- **Auditing skills/plugins:** `ecc:browser-qa`, `ecc:accessibility`, Chrome CDP
- **Page/component:** Roadmap course cards; curriculum stream badge tooltip
- **Severity:** P2
- **Category:** Responsive reflow / overflow
- **Problem:** Invisible absolutely positioned tooltips contribute to root layout width even before they are opened.
- **Current behavior:** At 360 px, root `clientWidth=345` and `scrollWidth=448`; at 390 px, 375/448; at 1280 px, 1265/1296. Hidden `.stream-category-tooltip` rectangles extended to x=448 and x=1296.
- **Expected behavior:** Only the deliberate roadmap scroller may overflow; the document itself must remain viewport-width, and tooltips should be edge-aware.
- **User impact:** Horizontal page movement, clipped chrome, disorienting reflow, and poorer zoom/mobile use.
- **Files/lines/selectors:** `js/roadmap.js:653` (`.stream-category` markup); `css/style.css:1916` (`.stream-category-tooltip`).
- **Evidence/reproduction:** Open `index.html?preview=1`; measure `document.documentElement.scrollWidth` at 360, 390, or 1280 px before opening any tooltip.
- **Viewport/theme:** 360/390/1280 light; 390 dark also reproduced.
- **Recommended correction:** Contain non-open tooltips so they do not affect root overflow; add viewport-aware left/right positioning and wrapping for open tooltips. Preserve the roadmap's internal horizontal scroll.
- **Complexity:** Medium
- **Confidence:** High
- **Verification:** Verified

### F-002 — Tracker dialogs do not receive or contain focus

- **Auditing skills/plugins:** `ecc:accessibility`, `ecc:frontend-a11y`, `ecc:browser-qa`
- **Page/component:** Dashboard, Settings, Course, and Department dialogs
- **Severity:** P1
- **Category:** Keyboard / modal focus management
- **Problem:** `openModal` reveals an `aria-modal=true` dialog but does not focus it, make the background inert, or trap Tab.
- **Current behavior:** With `#openSettingsBtn` focused, opening Settings leaves focus on that background trigger. Pressing Tab moves to `#openDashboardBtn`, also behind the visible modal.
- **Expected behavior:** Focus moves to a deliberate element inside the dialog, cycles within it, Escape closes it, and close restores the opener.
- **User impact:** Keyboard and screen-reader users can interact with obscured content and may not discover the dialog.
- **Files/lines/selectors:** `index.html:471`, `index.html:519`, `index.html:561`, `index.html:582`; `js/app.js:1839`.
- **Evidence/reproduction:** Chrome CDP at 390 px: `inside=false` immediately after opening and after one Tab. Source shows only reveal/mount/icon refresh on open.
- **Viewport/theme:** All; verified 390 light.
- **Recommended correction:** Reuse the admin drawer's focusable-control/trap pattern or native `<dialog>.showModal()` with explicit initial focus, inert background, Escape, and focus restoration.
- **Complexity:** Medium
- **Confidence:** High
- **Verification:** Verified

### F-003 — Tracker dialog close buttons have no accessible name

- **Auditing skills/plugins:** `ecc:accessibility`, `ecc:frontend-a11y`
- **Page/component:** Dashboard, Settings, Course, Department modal headers
- **Severity:** P1
- **Category:** Name, role, value / icon control
- **Problem:** Each close button contains only a Lucide placeholder and lacks text, `aria-label`, or `aria-labelledby`.
- **Current behavior:** Assistive technology receives a generic/unnamed button rather than “Close Settings,” etc.
- **Expected behavior:** Every icon-only close control has a stable descriptive accessible name.
- **User impact:** Screen-reader users cannot reliably identify the close action among other buttons.
- **Files/lines/selectors:** `index.html:480`, `index.html:528`, `index.html:570`, `index.html:591`; selector `[data-close-modal]`.
- **Evidence/reproduction:** Source inspection; compare named admin close controls at `admin.html:485` and `admin.html:508`.
- **Viewport/theme:** All.
- **Recommended correction:** Add context-specific `aria-label` values and keep the icon decorative.
- **Complexity:** Low
- **Confidence:** High
- **Verification:** Source-only

### F-004 — Settings tablist lacks the ARIA tab interaction contract

- **Auditing skills/plugins:** `ecc:frontend-a11y`, `ecc:accessibility`
- **Page/component:** Settings tabs
- **Severity:** P2
- **Category:** Semantics / keyboard navigation
- **Problem:** A container has `role=tablist`, but child buttons are plain buttons; panels are plain divs; selection and relationships are not exposed; arrow keys are not handled.
- **Current behavior:** CDP found zero `[role=tab]` and zero `[role=tabpanel]`; all five `aria-selected` values were null. Click handling changes only `.active` classes.
- **Expected behavior:** Tabs expose `role=tab`, roving `tabindex`, `aria-selected`, and `aria-controls`; panels expose `role=tabpanel` and `aria-labelledby`; Left/Right/Home/End work consistently.
- **User impact:** Screen-reader users receive an incomplete widget model and keyboard users must Tab through every tab.
- **Files/lines/selectors:** `index.html:536`; `js/app.js:2276`; `.editor-tabs`, `.tab-btn`, `.tab-panel`.
- **Evidence/reproduction:** Source inspection plus CDP semantic count on the rendered preview.
- **Viewport/theme:** All.
- **Recommended correction:** Match the already implemented Admin Catalog tab pattern rather than creating another interaction model.
- **Complexity:** Medium
- **Confidence:** High
- **Verification:** Verified

### F-005 — Curriculum stream disclosure targets are only 13 px high

- **Auditing skills/plugins:** `ecc:accessibility`, `ecc:browser-qa`
- **Page/component:** Roadmap/course-card stream badges
- **Severity:** P2
- **Category:** WCAG 2.2 target size
- **Problem:** `.stream-category-trigger` removes all padding and border, leaving only the text line as the hit target.
- **Current behavior:** Chrome measured repeated visible triggers around 48–49 × 13 px.
- **Expected behavior:** Target size is at least 24 × 24 CSS px or qualifies through sufficient target spacing; the containing badge may be made the target.
- **User impact:** Touch, motor-impaired, and magnified-pointer users have difficulty opening curriculum details.
- **Files/lines/selectors:** `js/roadmap.js:654`; `css/style.css:1902`.
- **Evidence/reproduction:** Render the preview and inspect `.stream-category-trigger` bounding boxes.
- **Conformance limitation:** The 13 px measurement is verified. Adjacent-target spacing and other SC 2.5.8 exceptions were not measured, so this is a usability finding and conformance candidate, not a definitive WCAG failure.
- **Viewport/theme:** All sampled widths; both themes inherit the geometry.
- **Recommended correction:** Increase the actual interactive box without visually inflating every badge; keep a visible focus indicator.
- **Complexity:** Low
- **Confidence:** High
- **Verification:** Verified

### F-006 — Programmatic smooth scrolling ignores reduced-motion preference

- **Auditing skills/plugins:** `improve-animations`, `review-animations`, `emil-design-eng`; technical accessibility corroboration
- **Page/component:** Back to Top; stream “See more”; Admin Catalog editor
- **Severity:** P2
- **Category:** Reduced motion
- **Problem:** JavaScript always requests smooth scrolling while the reduced-motion CSS only changes CSS scroll behavior/transitions.
- **Current behavior:** Calls use `{ behavior: "smooth" }` unconditionally.

## F. Conflicting Recommendations

1. **Expressive identity vs quiet operational density.** Design-direction guidance supports the distinctive roadmap, dot grid, status colors, and academic personality. Design-taste guidance warns against repeated cards/pills and decorative effects. The safer choice is targeted simplification inside repeated metadata groups, not removal of the roadmap or a generic SaaS redesign.
2. **Internal roadmap width vs mobile reflow.** The product intentionally preserves a horizontally complex prerequisite map. Accessibility/browser guidance objects only to whole-document overflow. Keep the roadmap scroller; contain hidden tooltips and page chrome.
3. **Page-owned tokens vs one universal system.** Current documentation intentionally allows separate Auth/Admin/Tracker families. Design-system guidance favors consolidation. The safer choice is shared semantic rules (focus, target size, elevation names) while retaining page-family palettes.
4. **Motion polish vs reduced motion.** Interaction polish benefits from short feedback transitions, but user preference takes precedence. Retain non-motion confirmation (text, label, toast) and suppress only scrolling/transforms/keyframes when reduced motion is active.

No conflict warrants an immediate redesign. More authenticated browser testing is needed before changing dashboard/Admin density or dialog contracts.
